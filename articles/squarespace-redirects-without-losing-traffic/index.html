Change Squarespace URLs without sending visitors to dead ends

Build a redirect map, choose relevant destinations, and test the result before and after a URL change.

A redirect is a route from an old address to a new one. It is useful when a page moves, but it cannot repair an unrelated replacement page or guarantee that search traffic stays unchanged. The work begins before you edit a slug: decide which addresses genuinely need to change and what a visitor should find at each destination.

This guide gives you a small-site migration worksheet and an original test routine. The example URLs are fictional. We have not performed a traffic experiment on them, and the examples are not a promise that a particular redirect will preserve rankings.

First decide whether the URL needs to change

You can improve a weak headline, rewrite an opening, or update a service description without automatically renaming its address. In Squarespace, changing a page title does not require changing its slug. Blog post addresses include the blog collection slug, and a changed default post format applies to future posts rather than retroactively updating existing ones. Check the URL slug controls.

Before changing anything, write a one-sentence reason: “We are merging two outdated checklists into a complete current guide,” or “This service has been renamed and the old URL causes customer confusion.” “The URL could contain one more keyword” is usually a weak reason for creating migration work on its own.

Separate a title change from a move in your task list. Give the URL work an owner and a rollback note. If the site has important inbound links or active advertising, include those destinations in the review rather than judging the change from the navigation menu alone.

Build a one-row-per-address map

Start with a spreadsheet containing the old full URL, proposed full URL, reason, action, responsible person, and test result. Collect addresses from your actual pages, analytics, search reports, campaign links, and important downloadable documents. A visual redesign can hide an old page without removing the links that still lead to it.

Add a relevance note in plain language: “A visitor following the old link still gets the staff-photo service they requested.” If that sentence feels dishonest, the destination is wrong. For a retired seasonal offer, you might keep a useful explanation or let a removed page return a proper not-found response, depending on the actual business situation.

Google warns against redirecting many old addresses to an irrelevant destination such as the homepage. A suitable consolidated replacement is different: it should actually contain the information the old pages offered. Google's site-move guidance covers mapping and relevance.

Choose permanent or temporary deliberately

Use a permanent redirect for a lasting move and a temporary redirect when you intend to restore the original address. Google treats permanent and temporary redirects differently as canonicalization signals; neither category is a guarantee about a page's future position. Read Google's redirect documentation.

For a small permanent Squarespace move, the mapping syntax is /old-path -> /new-path 301. The old route must no longer resolve as an active page. Open Developer tools, then URL mappings; put more specific rules above broad rules. The panel works for domains connected to that Squarespace site, and it cannot redirect CDN image or file URLs. Squarespace documents the format and restrictions.

For our fictional team-photography page, the entry would be /team-photos -> /team-headshots 301. Create and check the replacement first. Save the previous page text and settings before disabling or renaming the old route, so reversing an accidental change is possible.

Use individual rules for a short list of important pages. A broad collection rule may be convenient later, but it deserves its own test cases. Do not paste an example into your live settings without replacing the sample paths and checking for conflicts with existing rules.

Test the whole journey, not just the new page

Opening the new page proves only that the new page exists. It does not prove that an old newsletter link reaches it. Use this repeatable review for every mapped address:

  1. Open a private browser window so you see the public experience.
  2. Enter the complete old URL exactly as it appeared in the inventory.
  3. Check the final address and read enough of the destination to confirm that it answers the old request.
  4. Use your browser's Network panel with its log preserved to check the first document response and any subsequent redirects. Record the status and destination.
  5. Open the final URL directly. Confirm it serves a working public page rather than another redirect, login, draft, or error.
  6. Follow a relevant internal link and the page's main action. Verify that the move did not strand the customer elsewhere.

A successful response alone is not evidence of indexing or usefulness. Google can identify error-like content served with a success status as a soft 404. Google's status-code reference explains the distinction. A beautiful “page not found” message with a success response is not a successful migration.

In your worksheet, save a compact test note such as “Old URL returns 301; final URL returns 200; correct service and contact link checked.” If there are several hops, identify the intermediate rule and try to point the original route directly to the final destination. Keep the old-to-new map even after the first review passes.

Understand which host controls the old address

A redirect instruction has to reach the server handling the old URL. Adding a rule on your new Squarespace site cannot change a response from an unrelated GitHub Pages address. That follows from Squarespace's connected-domain restriction: the new platform does not receive that old request in the first place.

For a shareable development preview, the practical handoff is to keep the preview clearly labeled and link people to the final site when it launches. For an established production domain, plan the old-host behavior and domain connection together. A domain purchase, a DNS change, and a page redirect are separate actions; writing a mapping spreadsheet does not perform any of them.

Check the move after launch

Update your own links to use the final addresses, review the new sitemap, and watch for unexpected missing pages. Google recommends retaining migration redirects for at least a year where possible and notes that search visibility can fluctuate during a move. Keep the migration guidance available while monitoring.

Our suggested review rhythm is immediately after the change, the next working day, and weekly during the initial rollout. This is an operating checklist, not a guaranteed recovery timetable. Record the exact date of the move and distinguish broken routes from changes in demand, new content, or other changes made at the same time.

If inquiries disappear, verify the contact journey before rewriting every title. If a specific old link fails, repair that mapping. The worksheet should make the next action obvious: one address, one intended destination, and a test you can repeat.

What to take away

  • Keep useful existing URLs unless there is a clear reason to move them.
  • Map each old address to a relevant working destination and test the old URL.
  • Squarespace cannot redirect a GitHub Pages URL it does not control.
